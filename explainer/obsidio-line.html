Obsidio · a performance siege, one idea at a time

The Obsidio Line

Nine optimizations took a small backend from buckling under load to serving every request on time. Here is each one on its own — what the kitchen was doing wrong, and the single change that fixed it. Read them in any order.

2 CPUs · 2 GB — the whole box mix 60% /price · 30% /stats · 10% /risk score = 1× + 3× + 10× served on time
01The brigade

Staff for two, not eight

Under its cap the container can still see every core on the host, so the runtime spins up workers for cores it can't use — and they just thrash. Pin the count to the two you actually get.

ResultGOMAXPROCS=2 — foundational. Stops the runtime overscheduling onto phantom cores.

02The pass

A counter that skips the line

A price lookup does almost no work, yet in one shared queue it sits behind a 50,000-round braise. Give /price and /stats their own path that never enters the risk queue.

ResultStructural win. The fast path stops waiting on the slow one — its p95 collapses.

03Technique

Braise without the mess

The naive braise created a fresh string and byte slice on every one of its 50,000 rounds — a mountain of garbage that kept the collector busy. Reuse a single fixed buffer instead.

Result~150k → 0 allocations per request. Keeps the garbage collector off the hot path.

04Batching

One stir, many pots

After each hash the CPU waits on the result before starting the next. Run several independent hashes at once and one chain's work fills another's wait.

Result+9% arm64 / +2% x86 (per-chain −25% / −5%). Bigger where the CPU has more latency to hide.

05The equipment

The pro range

Most server CPUs have a built-in SHA-256 instruction — a commercial range that cooks two pots at once. Detect it at startup, use it where present, and fall back to plain code where it isn't.

Result+22% — separated x86. Per-chain cost −52%. The first big structural win.

06The twist

Plate at the burner

Formatting each result inside the kernel removed a per-round hand-off to Go and cut hash cost 10%… yet the score didn't move. The real bottleneck had shifted back to the fast path — which is what pointed to the next fix.

The lessonA faster kernel, a flat score. Always measure the whole system, not the part you changed.

07The payoff

Watch the window

The hashing loop couldn't be interrupted, so quick requests waited behind a whole braise. Pause it briefly between chunks to hand out whatever is waiting, then resume — the braise loses nothing.

Result+54% — separated x86. Drink p95 43 ms → 10 ms. The single biggest win.

08Resilience

Triage the rush

In a rush you can't clear, the oldest request will blow its deadline even if you serve it now. Serve the newest that can still make it, and wave off the overflow at the door before it costs you.

ResultInsurance. A no-op today; under a rush that DQs a naive build at 5% errors, this holds it at 0.6%.

09The bonus

A blackout-proof book

The bonus rewards surviving a hard restart. No database needed: append each price update to a file and flush it to disk before replying, then replay the file on startup. The scored siege is read-only, so it never pays this cost.

ResultSurvives a hard kill. Free on the scored path — pure additive bonus.
