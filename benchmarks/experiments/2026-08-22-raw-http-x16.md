# Raw HTTP/1.1 server and sixteen-lane AVX-512 insurance (ported from Advait's branch)

Two items from `fork/advait` brought into the governor build `6808e7d`:
his raw-TCP HTTP/1.1 server (his Item B, measured +2.1% on his stack) and
his sixteen-lane AVX-512 SHA-256 batch path (his Item C, insurance for an
x86 grader with AVX-512 but no SHA extensions). Both were re-measured on our
stack on one fresh c7i pair (`obsidio-bench-us-east-1-us-east-1a`, Xeon
Platinum 8488C). **This instance runs the unchanged `6808e7d` build at
4.31–4.34M against 4.85M on the previous instance**; as before, only
within-bracket deltas are claimed.

## Item B: raw HTTP/1.1 server (`d3e2623`)

### Why

With risk cheap, `net/http` is the largest remaining CPU share on ~1.8M cheap
requests per run (ROADMAP item 1). Advait's server parses the four fixed
request shapes byte-wise into a reused per-connection `http.Request` and
writes each response with one `conn.Write` of a preassembled buffer. The
port keeps our single `route()` entry point, so the governor's response and
error accounting is identical on both servers; `writeJSON` short-circuits
into the raw writer. `RISK_HTTP=std` boots the stock server.

### Correctness

Fifteen wire tests validate the output with `http.ReadResponse` as the
reference: keep-alive, split and pipelined reads, `Content-Length` framing
for POST (split from its head and pipelined ahead of a GET), percent-encoded
and multi-parameter queries, the contract 404 shapes, the generic status-line
branch (405), `Connection: close` and HTTP/1.0, oversized heads and bodies,
chunked and malformed requests closing silently, `/risk` end to end through
the worker pool, and interleaved concurrent connections. Headers a handler
sets (`Server-Timing` under `RISK_TIMING=1`) pass through and are cleared.
`killtest.sh` passes through the raw server. The build gate and the remote
runner's `GODEBUG=cpu.all=off` test pass ran the suite on x86.

Bracket: **+1.90%** over the stronger control, −0.15% drift. Pooled three
against three: medians 4,314,644 → 4,384,997 (**+1.6%**), means +1.5%,

this SHA-NI processor), so the measured change is the server alone.

### Interpretation

The request count rises 1.8%, which is the score. The latency profile also
changes: `/price` and `/stats` medians rise from 3.4 to 4.1 ms (p95 9.5 →
10.2 ms against a 200 ms bar) while the `/risk` mean falls from 92 to
83 ms at the same p95; the weighted mean iteration falls 2.4%. The cheap-path
shift is consistent across all three candidate runs and is recorded as an
observation rather than explained.

**Verdict: kept.** Gain inside the protocol's 0.5–2% band, accepted on a
bracket plus a repeat pair with disjoint ranges.

## Item C: sixteen-lane AVX-512 kernel (`8badba2`)

### What it is

minio/sha256-simd v1.0.1's AVX-512 multi-buffer routine (Apache-2.0,
vendored unchanged with its licence) wrapped for the fixed chain shape: each
lane is the chain's 64 hex bytes plus the constant padding block, one call
advances sixteen chains by one round, yields follow the scalar kernels'
cadence. The round table is generated from the 64 FIPS constants.

Gate, in order: AVX-512 F/DQ/BW/VL in `/proc/cpuinfo` and no SHA-NI
(`RISK_X16=on` races it on SHA-NI boxes for A/B use, `RISK_X16=off` kills
it); a differential self-test against `crypto/sha256` including equal-lane
inputs and a 300-round chain on every lane; a timed race against the path it
would displace (four quads with SHA-NI, four portable chains scaled by four
without) that must win by 30% (10% when forced) and sets the minimum batch.
A worker takes up to sixteen parked jobs when the path is live and that
many are parked; short pops fall back to the lane kernels.

### Level 0 on the Xeon 8488C

All x16 tests pass (lane layout, 5,000 random sixteen-lane hashes against
the standard library, full and partial chains and worker batches against the
reference digest, self-test and race, concurrent hammer). Boot logs:

| Regime | Log line |
| --- | --- |
| default (SHA-NI present) | `AVX-512 present, SHA-NI kernels preferred` (path off) |
| `RISK_X16=on` on SHA-NI | enabled, 1.20× over four SHA-NI quads, minimum batch 15 |
| `RISK_SHANI=0 GODEBUG=cpu.sha=off` | enabled, **7.45×** over the portable path, minimum batch 4 |

On a SHA-NI processor the path is flat by Advait's measurement (−0.26%) and
stays off by default; it is insurance only.

### Simulated no-SHA-NI grader, exact grader

`RISK_SHANI=0 GODEBUG=cpu.sha=off` disables both our SHA-NI kernels and the
standard library's SHA-NI path (the vendored `x/sys/cpu` prints an
"unknown cpu feature" warning for the second option; `internal/cpu`, which
`crypto/sha256` consults, applies it). Control: the same with `RISK_X16=off`.

| Run | Regime | Work score | Requests | Errors | Price p95 | Risk p95 | Bars |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| A1 | portable (`f6d4de0`) | 769,042 | 317,120 | 0.723% | 20.7 ms | 408 ms | 4/4 |

**4.28× the stronger control** (+0.5% drift) on a grader without SHA
extensions but with AVX-512; the bars pass in both regimes. The portable regime is the floor for
a grader with neither.

**Verdict: kept as insurance.** Off by default on SHA-NI processors, gated by
self-test and race, kill switch `RISK_X16=off`.

## Testbed check: the load generator is not the cap

Sampled at the 200-VU peak of a screen of the final build
(`loadhost-cpu-x86-screen-20260822`): the c7i.large running k6 was 23–40%
busy over twelve one-second samples; the target host read a flat 50% of its
four vCPUs, i.e. the container pinned at its two-CPU quota. Two results
tonight could have been read as generator saturation (the raw server raising
throughput while cheap latency rose; the sixteen-lane path flat on SHA-NI);
they are not. Between-instance differences are the target's own speed.
