# Go PGO experiment

## Hypothesis

Go 1.26.6 profile-guided optimization might improve the accepted compact-hex
server without changing its algorithm. The experiment was deliberately isolated
from all source-level optimizations.

## Training input

- Source: accepted compact four-at-a-time hex-unrolling champion.
- Training workload: the unmodified 90-second `benchmarks/screening.js` mix.
- Target: Linux arm64 container capped at 2 CPUs and 2 GiB.
- Profile duration: 95 seconds, covering the complete ramp.
- Go toolchain: pinned Go 1.26.6 builder used by the submission.
- Raw profile: `benchmarks/profiles/pgo-20260822/default.pgo`.
- Profile SHA-256: `34c0ca95c0ed4cfb6e3ae3b6360b9382677c3687b6a908786a11c86ba6ce2bbe`.

The training run completed 399,397 correct requests, scored 997,584, returned
zero errors, and passed every published latency threshold. Its CPU profile was
representative of the scored bottleneck: `encodeDigest` accounted for 58.22%
of samples and the SHA-256 block implementation for 24.10%.

## Level 0 result

The control and candidate used the same source and toolchain. The only build
difference was `-pgo=off` versus the captured profile. Eight one-second
`BenchmarkRisk` samples produced:

| Build | Median | Range | Allocations | Bytes allocated |
| --- | ---: | ---: | ---: | ---: |
| Control, PGO off | 3.600 ms | 3.559–3.650 ms | 0 | 2 B/op |
| PGO candidate | 4.309 ms | 4.261–4.367 ms | 50,000 | 6,400,010 B/op |

PGO made the kernel 19.67% slower and caused one allocation per feedback
iteration. Correctness still passed both normally and with
`GODEBUG=cpu.all=off`, but the allocation and speed regression fail the Level 0
promotion gate by a wide margin.

The profile is dominated by the risk call graph, and Go applies PGO to
transitive dependencies as well as the main package. The exact compiler
transformation responsible for the new allocations was not proven; that is not
necessary for the decision because the measured regression is large and
repeatable.

## Verdict

**Reject PGO and do not run screening or AWS comparisons.** No submission source
or Dockerfile change is retained. Revisit only after a Go toolchain change or a
specific compiler-level explanation that can be tested independently.
